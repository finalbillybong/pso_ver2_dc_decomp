# Five-function matching proof

All five selected functions from the European PSO Ver. 2 executable compile
from the checked-in C sources to their original bytes. This proves a usable
matching workflow for these samples. It does not establish the cost or
completeness of a whole-game decompilation.

## Verified configuration

- Compiler: Metrowerks C/C++ Compiler for Dreamcast (SH), version 2.4,
  Engineering Build, runtime built March 21, 2000 at 15:31:29.
- Compiler SHA-256: `23fd6265e00e054e7746c58859f02d841dbcbc73d7310d524e55bab5c5a0c0f3`.
- Options: `-proc SH4 -endian little -mw_fp hardware -Cpp_exceptions off -O2`.
- Linker: locally built GNU binutils 2.44, `shlelf`, explicit original address,
  no relaxation. The original game linker has not been identified.
- Runner: hash-pinned wibo 1.2.0. Installation changes remain in scratch.

The compiler is archived in the R10.1 SDK directory of
[dreamcast-docs at a pinned commit](https://github.com/Kochise/dreamcast-docs/tree/58027aeb669a80aa783a6d2cdcd2d161fd50d359).
Exact download paths and hashes are in `config/matching-packages.json`.
Compiler command-line help and the archived Metrowerks *Targeting Dreamcast*
manual informed option selection. No license bypass or compiler patch is used.

This compiler/configuration is demonstrably compatible with the five samples;
byte equality does not uniquely identify the original compiler binary or flags.
Other parts of the executable may have used different compilers or settings.

The five entry addresses and complete ranges were fixed before the GCC and
CodeWarrior experiments. None was substituted to increase the match count.
The initial inferred mask function name was corrected after reviewing its
`TST`/`SUBC`/increment sequence: it returns whether any masked bit is set.

Boundary review checked contiguous instructions, return and branch paths,
delay slots, incoming references, PC-relative literals, and neighboring code.
The manifest includes reference sites and SHA-256 hashes for each range.
Specifically, the loop owns the four-byte `0x80` literal at `0x8c027cf8`;
the call sample includes two padding bytes and the four-byte target address
`0x8c02a980` at `0x8c029fa0`. Every byte is compared.

The sources use ordinary C. `Object` is only a partial layout showing the
observed field at offset `0x34`; the real class and predicate meaning remain
unknown. `Vec3` expresses the observed float accesses at offsets zero and eight.
The external predicate address is expressed as a function pointer in C.
There are no assembly bodies, instruction-byte arrays, or output patches.

## Controlled compiler comparison

The final matrix uses the final sources for every candidate: 19 configurations
times five functions, for **95 builds**. Results and hashes are recorded in
`config/compiler-matrix.json` and regenerated by `tools/match_matrix.py`.

| Configuration | Exact matches |
| --- | ---: |
| Hitachi SHC 5.0r31, 5.1r01, 5.1r13; each at 0/1, default/size | 0/5 each |
| CodeWarrior O0 or O1, exceptions off, hardware float | 0/5 each |
| CodeWarrior O2, exceptions off, hardware float | **5/5** |
| CodeWarrior O3 or O4, exceptions off, hardware float | 4/5 each |
| CodeWarrior O2, exceptions on, hardware float | 0/5 |
| CodeWarrior O2, exceptions off, software float | 4/5 |

O3/O4 allocate the loop's registers differently. Exception-enabled output
introduces different frame handling; the call sample also adds allocated
exception data and is rejected by the strict sample adapter. Software float
requires unresolved runtime helpers for the float sample and is rejected.
These are failures of those tested configurations for these sources, not proof
that no possible source could match under another setting.

An earlier exploratory GCC 2.95.3 experiment also produced different code.
It is not part of the final reproducible matrix and does not rule out Sega's
modified GCC releases or other GCC settings.

## Reproducibility and limits

`tools/verify_matches.py` builds each sample twice in new temporary compilation
directories and verifies identical exact outputs. It also checks that changing
the mask constant or call target fails byte comparison, changed source receipts
and modified compiler copies fail validation, and unresolved symbols remove
stale output and fail linking. `config/matching-validation.json` records the
source, sample, toolchain, and resulting output hashes.

The compiler driver does not read the game binary. It validates the linked
entry address and complete executable section, rejecting additional allocated
data and unresolved relocation sections. `pso.py compare` independently checks
the pinned decoded image and current build receipts before comparing bytes.

The initial 19 unit tests cover extraction, reference integrity, strict
comparison, and ELF validation. This initial proof did not require emulator
execution. The ongoing reconstruction has since expanded to 18 matching
functions and a title-screen boot of an integrated, reference-backed image;
see [current project status](PROJECT.md). Shared headers, general external
symbol handling, translation-unit layout, assets, and gameplay validation are
outstanding parts of that work. The initial 128 compared bytes are diagnostic
examples, not a whole-game percentage.
